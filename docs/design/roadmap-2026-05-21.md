# Strategic plan — 2026-05-21

A planning pass after F1.2 step 6a + the DevEx round + the upstream
issues filed (ggml-org/ggml#1501, OriPekelman/tep#13). Goal:
prioritise + frame what to build next, with a particular eye toward
the inference-serving sweet spot.

## Where this project sits today

What's distinctive about the code we already have:

1. **Single-binary deployment.** Spinel AOTs a Ruby app + linked C
   libs to one ELF. No Python, no PyTorch, no runtime to install.
   `scp` the binary, run, serve.
2. **Phase 2 mmap (BYO-pointer).** Weights ARE the GGUF file's
   mmap'd pages — on unified-memory SKUs (GB10 / Jetson / DGX Spark),
   CUDA kernels read host file pages directly via UVA. **Realize+attach
   takes 30 ms instead of 30 s.**
3. **Phase 3 Q8-stays-Q8.** Quantized weights stay quantized in memory;
   no load-time dequant cost. 7B-Q8 in 9.4 GB RSS instead of 30 GB.
4. **Generic loader.** `Arch.from_gguf(path)` introspects the file
   and constructs the right config; `ToyLM.new(arch, :cpu)` /
   `.load(path)` runs any supported architecture. Same Ruby code,
   12 supported models.
5. **Tokenizer-in-GGUF.** Vocab + merges live in the GGUF; no Python
   tokenizer required to serve. Ruby BPE encoder/decoder ships for
   Llama-family and Qwen2/3.
6. **Honest acceptance gates.** Token-ID parity tests
   (`demos/qwen25_acceptance`) catch any graph-builder regression in
   ~30 s on 4 model sizes.
7. **In-graph autograd + LoRA training.** F1.1+ ships a working
   forward+backward+opt_step path through ggml. F1.2 step 6a trains a
   real model (SmolLM2-135M) with LoRA-Q.

Honest perf state (gx10 GB10 / Grace Blackwell):

| Model              | CPU tok/s | CUDA tok/s | llama.cpp same hw |
|--------------------|----------:|-----------:|------------------:|
| SmolLM2-135M       | 106       | 82         | ~400              |
| SmolLM2-360M       | 48        | 42         | ~150              |
| Qwen2.5-0.5B       | 38        | 43         | ~150              |
| TinyLlama-1.1B     | 21        | 23         | ~80               |
| Qwen2.5-1.5B       | 15        | 20         | ~60               |
| Qwen2.5-3B         | 7.6       | 11         | ~50               |
| Qwen2.5-7B Q8      | 5.7       | n/a (Q8 alignment, fixable) | ~35              |

**CUDA is only 1.0–1.4× CPU at our model sizes today because the
per-step graph rebuild dominates compute.** Once task #69 (M3,
reusable decode graph) lands, we estimate 5-10× current CUDA perf
on ≥1B models — which would put us **within ~2× of llama.cpp** on
the same hardware. That's the realistic ceiling without ditching
ggml as the kernel layer.

## The local-inference landscape

What others do, what they trade:

| Project          | Bias                          | Strengths                                                      | Weaknesses                                                                                       |
|------------------|-------------------------------|----------------------------------------------------------------|--------------------------------------------------------------------------------------------------|
| **Ollama**       | Model swapping, dev UX        | One-command pulls, easy swap, OpenAI compat, registry          | Each swap = full disk→memory load. Single-user. Wraps llama.cpp via Go shim.                     |
| **vLLM**         | Max throughput single model   | PagedAttention, continuous batching, 100s tok/s aggregate      | Python + GPU server. Single model per process. Heavy install.                                    |
| **llama.cpp**    | Portable speed                | C++, small binary-ish (server.exe), fast, every backend        | Operations footprint (no model registry, no per-user adapters), C++ ergonomics                   |
| **TGI** (HF)     | Production single-model       | Continuous batching, tensor parallel, Rust+Python              | Single-model, heavy deps, big team to operate                                                    |
| **TensorRT-LLM** | NVIDIA peak perf single model | Top NVIDIA throughput                                          | NVIDIA-only, hard to use                                                                         |
| **MLX**          | Apple Silicon                 | Native Mac perf, decent UX                                     | macOS-only, model coverage narrower                                                              |
| **LM Studio**    | Desktop GUI                   | Friendly desktop                                               | Not a server, not a stack                                                                        |
| **Candle**       | Rust ML                       | Single binary, no Python                                       | Smaller community, fewer models, less battle-tested                                              |

Two axes show through the table:

```
                        (single model, max perf)
                         vLLM ── TGI ── TRT-LLM
                                  │
                                  │
   (multi-model, easy swap)       │     (portable speed)
   Ollama ───── LM Studio        toy?    llama.cpp ── Candle
                                  │
                                  │
                                  │
                                MLX  (one-platform native)
```

Almost nobody sits in the **"swap many models, share file-page memory,
small footprint, simple ops"** corner. Ollama gestures at it but each
swap costs full reload. llama.cpp can do it via mmap but doesn't
present that as a story. The pieces fit our infrastructure exactly:

- mmap means swap is a metadata operation, not a data operation.
- Single binary means deployment is one file.
- Generic loader means N models in a `models/` directory all work
  the same way.
- Phase 0 acceptance gates mean the swap can be tested for parity.

## The proposed sweet spot — "Toy as a multi-model, swap-friendly inference daemon"

**One ELF + a directory of GGUFs + an HTTP port.** A single request
specifies which model to use. The daemon mmap's the requested model
on demand (microseconds when warm-cached, milliseconds when cold);
KV cache for each in-flight context is the only per-request memory
cost beyond the file's page cache.

Concretely, the daemon would:

- Discover models from `models/*.gguf` at startup. Build an `Arch`
  per file (~5 ms each). Hold them in a small index.
- Accept OpenAI-style `POST /v1/completions` with a `model:` field.
- Lazily activate a model on first request via Phase 2 mmap-attach
  (~30 ms). Keep it active until idle eviction.
- Reuse KV-cache buffers across requests within the same model (one
  KV-cache pool per model, sized for max-concurrent).
- Stream tokens (`stream: true`) — modest addition to current Tep
  handlers.
- Hot-load LoRA adapter directories (`adapters/<name>/*.gguf`)
  per-request. Cheap because adapters are tiny relative to base
  weights and the base is already mmap'd.

**What this gives a user**: a single binary they can drop on a box,
point at a directory of models, and have an OpenAI-compatible
endpoint that handles N models + M adapters with no Python and no
per-model warmup cost.

**What this does NOT give**: vLLM-level aggregate throughput for one
model under heavy load. We won't beat continuous-batching specialists
on max QPS. That's their territory.

The pitch in one sentence: **"the smallest ops surface in local
inference: one binary, file-system-of-models, model swap is free."**

## Performance ceiling without architectural changes

Today's hard ceiling on our current code:

- **Inference**: ~CUDA matches CPU because of per-step graph rebuild
  (task #69's M3 would unlock 5–10× CUDA, ~2× CPU once SIMD path
  warms up). After M3 we'd reasonably hit:
  - SmolLM2-135M CUDA: 200-300 tok/s
  - Qwen2.5-3B CUDA: 40-65 tok/s
  - Qwen2.5-7B Q8 CUDA: 30-40 tok/s (after the d_ff-alignment fix
    for ggml-cuda)
- **Training**: CUDA path works correctly + at reasonable speed
  (33 SGD steps/sec on SmolLM2-135M r=16). CPU path blocked on
  ggml-org/ggml#1501 (sched aliasing).
- **Concurrency**: today's tep_demo serves one request at a time
  (each request runs to completion before the next is dispatched).
  Multi-tenant requires either fork-per-request (Tep's prefork
  mode) or proper KV-cache pool + continuous batching.

What we CAN'T do without rewriting the inference path:

- vLLM-level batching (continuous batching, PagedAttention). That's
  a different architecture; our forward graph is single-sequence.
- Tensor parallel across multiple GPUs. We assume one device.
- KV-cache compression (offload to host, swap pages). Possible but a
  project.

(longer arc).

## What we should NOT chase

- vLLM-shape continuous batching. Different architecture, not our
  fight, won't out-engineer them.
- A custom kernel layer. ggml is good enough and well-maintained; we
  contribute back via upstream patches (concat-back, BYO-pointer,
  cpy-strided).
- Multi-GPU / tensor parallel. Until single-device is saturated.
- A web UI. Belongs in a separate project (LM Studio's territory).
- A new model converter. `prep/convert_*` works; quirks in upstream
  GGUFs are bug-by-bug, no large refactor needed.

## Three concrete decisions to make

1. **Do we want to be a sweet-spot inference daemon?** If yes, the
   next 4-6 weeks of work is M3 + multi-model registry + streaming
   + adapter swap. If we'd rather stay a focused "read this code, see
   how a transformer works" educational repo, much smaller scope.
2. **Do we wait for upstream fixes (Tep#13, ggml#1501) or work
   around them?** Workarounds work but accumulate. Waiting blocks
   visible polish but is honest about the state.
3. **CPU/CUDA strategy for training.** With ggml#1501 open, CPU
   training is unreliable. Two paths: (a) stay CUDA-only for
   training, document, ship; (b) keep digging into ggml-cpu's
   allocator. (a) is what F1.2 step 5+6a already does and works.

My recommendation, since you asked for one: **(1) yes, sweet-spot
inference daemon; (2) wait for Tep#13 since the workaround is just
adding `, false` and the right answer is upstream; (3) CUDA-only
training for now, log the upstream issue, move on.**
