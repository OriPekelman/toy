## THE RESULT — already measured, do not re-derive

Fair cell: **lr 0.03, 2000 steps, seed 0, matched init**, delayed-cue
task at the lane defaults (1 layer, hidden 64, features 24, T 64,
4 classes, batch 32):

| arm | val accuracy | graph bytes |
|---|---|---|
| BPTT (`chain`) | **1.000** | 13 289 988 |
| DFA `--dfa-cut layer` | 0.996 | 13 513 224 |
| **DFA `--dfa-cut step` (no BPTT at all)** | **0.992** | 15 578 112 |
| `frozen` | 0.203 | 13 289 988 |

**The headline: on a gated LSTM the per-step cut MATCHES BP** (.992 vs
1.000) and crushes the frozen control — whereas on toy#155's selective
SSM the *identical* cut collapsed to chance (.250 vs BP's 1.000). Same
task generator, same cut axis, opposite outcome. That is the
cross-architecture finding this lane exists to produce, and it agrees
with Folchini et al. (ISC-HPC 2025), which toy#157 cites.

**The memory half of the success target is NOT met**, now measured in
the units the ticket asks for: the step cut uses **17% MORE** bytes
(15.58 MB vs 13.29 MB), confirming toy#155's node-count result with a
better instrument. Same structural reason: in a graph autodiff every
forward tensor is materialised whatever the credit rule, so the
streaming win is not expressible as a graph rewrite. **Already filed as
`tao#21`** ("The BPTT activation-memory claim (F19 + F21) is not
measurable in toy as built"), with both lanes' tables, the reason, and
three options for what would actually measure it — the cheapest being an
ANALYTIC streaming-bytes figure alongside the measured graph bytes. It
also recommends NOT spending tao#19's deferred F19 CUDA twin, since a
device port changes throughput and not what the graph materialises.
Reference tao#21 from the toy#157 comment rather than restating it.

Still TODO on the measurement side: **seeds 1 and 2** at the fair cell,
and a **graph-bytes sweep over `LSTM_SEQ`** ({16, 32, 64, 128}) so the
memory claim is stated as a function of L, which is how the ticket

## TWO CORRECTIONS I MADE TO MY OWN WORK — both would have shipped a wrong result

1. **The first LSTM had NO gate biases.** f_t = sigmoid(0) = 0.5 at
   init, so the cell state halves every step and 0.5^64 is nothing: the
   carry was dead before training started. That produced
   **BPTT .199 / DFA-step .969** — a spectacular-looking "DFA beats
   BPTT" that was really a crippled LSTM. Fixed by adding the four gate
   biases with **b_f initialised to 1.0** (Jozefowicz et al. 2015). The
   comment in `lstm_engine.rb` records this; keep it.
2. **Even after that, BPTT sat at chance until swept properly.** At
   lr 0.003 (the inherited default) and 600 steps, chain reads .254 —
   chance. It needs **lr 0.03 AND 2000 steps** to reach 1.000. At
   lr 0.03/600 it is .199. So a lane stated at the default LR would
   have reported "DFA beats BPTT" for the second time, wrongly.
   **The gate must pin lr 0.03 / 2000 steps and say why.**

**RESOLVED:** the runner's default LR is now **0.03** (it had been 0.003,
inherited from the ssm lane and never re-measured), with the full sweep
recorded at the constant, and `prep/fixtures/train_lstm_baseline.txt`
regenerated against it. `toy train lstm` out of the box now trains a
`chain` arm that can actually learn its own task.

## Structural facts to preserve in the gate

- **No `--align-events` on this lane.** The DFA update arrives through
  autodiff from the surrogate roots, so it lands in the SAME accumulator
  a BP run uses and there is no second tensor to take a cosine against.
  toy#158 hit this first; toy#155 restated it. Gate on **the B seed
  moving the dfa curve and being inert on chain** instead.
- **Forward identity.** `tnn_detach` is forward-identity, so step 1
  under `dfa` must be byte-identical to `chain`, and steps 2+ must
  differ. That is what makes the arms comparable at all — assert both.
- **One tap family is enough here**, unlike the SSM lane: `h_t` IS the
  layer output and it reaches the prediction from every step. The SSM
  lane needed a second family because its per-step layer output was
  inert at the final layer.
- **`--task mean`** is the degenerate control (toy#155's, reused): the
  class signal is spread over every step so neither memory nor selection
  is needed. Assert its degeneracy rather than assuming it.
- Suggested gate legs, mirroring `prep/ssm_gate.rb` (which is the
  closest template): fixture + chain byte-null, determinism,
  forward-identity + arm effect, B seed, wiring/bundle (tap counts,
  `cut` provenance, `graph_bytes`), the MANDATORY success bar at the
  fair cell, the **cross-architecture contrast** (step cut matches BP
  here, collapses on ssm — worth an explicit leg with a pointer to the
  roadmap), the memory measurement, `--task mean`, fail-loud, CLI.

## Landmines that fired this session (all already recorded, but they recur)

- **Unreachable graph input = no backend buffer.** An input tensor
  nothing consumes aborts inside `ggml_backend_tensor_set` on upload.
  Fired on toy#155 (the state-tap B under the layer cut). Guard with a
  "does the graph use it" check before allocating a feedback matrix.
- **`pkill -f "make gates"` kills the calling shell too** (exit 144).
  Kill by PID instead.
- **The gate battery takes ~2.5 h** and `franken_moe_cli_gate.rb` is
  most of it. Run it in the background and do NOT run heavy sweeps
  concurrently — CPU contention roughly tripled its wall time.
