## The mechanism as built

K3 / DeepSeek-V3 form. The MTP module reads the main model's hidden state
at position `i` together with the embedding of the **next** token,
projects the pair back to `d`, runs one block mirroring a backbone layer,
and predicts token `i+2` through the **shared (tied)** head:

```
h'_i    = M [ RMSNorm(h_i) ; RMSNorm(Emb(t_{i+1})) ]      M is [d, 2d]
logits2 = Head( Block(h'_i) )
loss    = CE_main(t+1)  +  lambda * CE_mtp(t+2)
```

Tying the head is what makes this one extra block rather than a second
model.

### Two toy-scale identifications, stated not hidden

- **`h_i` is taken as `x_final`**, the hidden state *after* the final
  norm. That norm **is** the `RMSNorm` the formula puts on `h`, so this
  is the same quantity, not an approximation.
- **The next-token embedding rides its own `i32` id input**, not a
  shifted view of the embedding rows. A strided view used as a `mul`
  operand has a poisoned backward (the `ggml_is_padded_1d` family that
  bit ShortConv and MLA). The runner uploads ids shifted by one; the
  value is identical and the gradient path is clean.

### Decisions that are load-bearing

| decision | why it matters |
|---|---|
| MTP weights allocate **after** the layer loop and draw **last** from the init stream | `--mtp` on and off share an identical backbone init, so a with/without comparison isolates MTP |
| `[d,2d]` projection registered via `ft_add_global_2d` | the existing globals optimizer walker steps it for free |
| explicit optimizer arm for the **block's** tensors | without it the module builds, produces a loss, and never trains |
| explicit **moment zeroing** for the block | `seq_blocks_ffi` does not contain it, so the normal loop misses it; un-zeroed Adam `m`/`v` corrupt the first updates *silently* |
| second CE root patched **identically** into `build_training_step` and `build_training_step_franken` | those two must emit the same graph under an empty policy — the parity gate pins it |
| reported step loss stays the **main** CE | a `--mtp` curve is directly comparable to one without it, instead of being offset by a term measuring a different prediction |

## What remains

1. **Shift-by-k labels.** `Toy::Labels.next_token` clamps at the window
   edge (`k+1 < context ? seq_ids[k+1] : seq_ids[k]`). A `next_token_k`
   needs the same clamp discipline for `k=2`, and the last **two**
   positions have no true t+2 target — decide explicitly whether they
   clamp or are masked out, and say which in the provenance.
2. **Per-step upload.** Do it through an engine setter called *before*
   `recipe.step!`, uploading the shifted ids and the t+2 one-hot. This
   deliberately avoids changing `step!`'s signature and so touches no
   recipe call sites.
3. **CLI**: `--mtp`, `--mtp-lambda`, plus a flag×recipe matrix row.
4. **Telemetry**: `mtp_loss` alongside the step loss; `mtp` + `mtp_lambda`
   in provenance; cost accounting must grow by the projection and the
   extra block (the third instance of that silent-under-count class —
   see K4b and toy#145).
5. **Eval**: t+2 accuracy in the `eval_ce` event.
6. **Gate leg.** Minimum bar, mirroring what the recent tickets learned:
   - `--mtp` off is byte-null (already true; pin it);
   - the MTP weights **provably move** (a signature over them, start vs
     end) — the K4b/`experts_sig` lesson: a module that builds and
     reports a loss but never trains looks healthy on a curve;
   - `--mtp-lambda 0` must leave the **backbone** curve byte-identical to
     `--mtp` off while the MTP weights still receive gradient — that is
     the clean separation of "the second root exists" from "the second
     root perturbs the main path";
   - provenance and cost grow.

## Open questions worth deciding before finishing

- **Window-edge targets.** At `context=T` the last two positions have no
  genuine `t+2`. Clamping biases the MTP loss toward repeated tokens;
  masking needs a zeroed label column. Clamping matches what
  `next_token` already does for t+1 and is the smaller change — but it
  should be a stated choice, not a default that quietly skews the second
  loss.
- **Does the MTP block mirror the *backbone kind*?** It is currently a
  plain `TransformerBlock`. In a `--layer-pattern k3` stack the backbone
  blocks are KDA and Gated MLA, so "mirroring a backbone block" arguably
  means matching the kind. Simpler now, worth revisiting when toy-k3 is
  composed.
- **Inference-side EAGLE-3 / LK loss** is explicitly out of scope here;
  M10 as scoped is the training-time layer plus its CE root.

## BLOCKER RESOLVED (2026-08-05)

`--mtp 1` ran the module. The guard is removed.

**None of the three suspects was the cause.** Recorded because the
wrong-suspect list cost a session:

1. `tnn_input_2d_f32_persistent(d, 2d)` **was correct as assumed.**
   Verified in the C, not re-reasoned: `tinynn_ggml.c:522` does
   `ggml_new_tensor_2d(ctx, F32, cols, rows)`, so `(rows, cols)` yields
   `ne = [cols, rows]` and `(d, 2d)` really is `ne = [2d, d]`. The
   "(out, in)" convention taken from `reg2` was sound.
2. The `concat` dim-0 result was exactly `d + width(e_n)`.
3. `x_final.ne0` **is** `d_model`, as assumed.

**The actual cause: the E2.3 projection lens.** The rig runs with
`seq_donor_d_in = 128` while `d_model = 64`. The raw
`t_seq_token_embed` is therefore **donor-width**, and the main path
projects it down through `t_seq_w_proj` (the `x_embed` block). The MTP
path read `e_next` straight off the raw table, so it was `d_in`-wide:

```
MTPDBG x_final ne=64,32      <- d_model = 64
MTPDBG e_next  ne=128,32     <- d_in = 128, NOT d_model  ** the bug **
MTPDBG pair    ne=192,32     <- 64 + 128, not 2d = 128
MTPDBG proj    ne=128,64     <- correct all along
MTPDBG embed   ne=128,627    <- table is donor-width
MTPDBG donor_d_in=128
```

`mul_mat` needs `proj.ne0 (128) == pair.ne0 (192)` → assert. The fix
routes `e_next` through the same lens the main path uses, rather than
assuming table width == `d_model`.

**METHOD NOTE, the transferable part.** The shapes were settled by
dumping `tnn_tensor_ne0/1/2` at each step of the MTP path and reading
them, which took one build. Three sessions of reasoning about which
tensor "should" be what did not converge; the helpers were already
FFI-bound (`lib/toy/ffi/tinynn.rb:593`). Dump the shapes first.

**Also**: `llama_arch_cuda.rb` is **GENERATED and gitignored**, not a
hand-mirrored twin like the MoE runners. It needs no manual edit — the
generator carries the fix. Do not hand-edit it.
