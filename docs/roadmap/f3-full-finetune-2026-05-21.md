# F3 — full fine-tune on CUDA

**Status:** in-flight 2026-05-21.
**Tasks:** #63.
**Predecessors:** M3 step 3 (seq-mode forward + LoRA + AdamW
training graph). F4 step 1 (QLoRA via Q8 base, CPU).

## Goal

Train **every** parameter of a llama-family model end-to-end on
CUDA (and CPU for the regression check). Replaces LoRA's
adapter-only training with first-class gradient + AdamW state on
every weight tensor.

## Scope (MVP)

- SmolLM2-135M as the model (~134M params; comfortably under the
  GB10's 121 GiB budget at 16 B/param ≈ 2.1 GB).
- F32 base only (Q8 base for full FT is its own follow-up; gradient
  flow through a quantized weight is technically supported via
  ggml's matmul backward but mixes dtype with the adapter and adds
  more risk surface).
- Train per-block weights only: RMS-norm gammas, Q/K/V per-head
  projections, O projection, FFN gate/up/down. **Skip embeddings
  and the final-norm gamma** (the bulk of the model is in the
  per-block weights; freezing embeddings is a common SFT recipe
  and shrinks the param count by V × d_model). Adding embeddings
  later is a one-line set_param + opt_step addition.
- Same seq-mode forward graph; same `build_training_step`
  topology, just with opt_step nodes attached to more weights.

## Memory budget

Per parameter we pay 16 B (F32 throughout):
- weight: 4 B
- gradient (from autograd): 4 B
- Adam m + v: 8 B

SmolLM2-135M per-block params: ≈ 121 M (134 M total – V × d × 2 –
d for final norm). At 16 B/param: **~1.94 GB** of optimizer
state. Plus activations (a few hundred MB at T=4). Comfortably
under 8 GB.

## What changes from F2 / M3 step 3

In `lib/llama_seq_forward_ffi.rb`:

1. New flag `seq_full_finetune_enabled` + `enable_full_finetune!`
   setter. Mutually exclusive with `enable_lora_q!`.
2. New `realize_for_full_finetune(gguf, cfg, t_seq, untied, qkv_bias)`
   method. Same shape as `realize_for_mmap` but:
   - Per-block weight allocators swap
     `tnn_input_2d_persistent_mmap` (read-only, file-page-backed)
     for `tnn_input_2d_f32_persistent` (writable F32 in ctx_w).
   - For each writable weight, also allocate Adam m and Adam v
     (same shape, ctx_w).
   - `tnn_set_param` on every writable weight.
   - After `tnn_finalize_weights`, copy values from the GGUF
     via the existing `tnn_gguf_copy_to_persistent` /
     `tnn_gguf_copy_1d_to_persistent` /
     `tnn_gguf_copy_head_slice_to_persistent_native` primitives
     (these dequantize Q8 / BF16 / etc. into F32 on the fly).
   - Zero-init Adam m and v.
3. `build_training_step` extended: when full-FT enabled, emit
   `tnn_opt_step_adamw` for every (weight, m, v) triple, not just
   the LoRA pairs.

Each block stores parallel arrays of `(weight, m, v)` triples so
`build_training_step` can iterate without per-tensor casework.

## Acceptance

- `demos/smollm2_seq_full_finetune` (CPU) and
  `demos/smollm2_seq_full_finetune_cuda` build clean.
- CE decreases monotonically over 10 steps on the same fixed
  T=4 / TARGET_ID smoke as `examples/03_finetune_lora`.
- Loss curve is faster than the LoRA equivalent at the same LR
  (more capacity → bigger steps). Acceptance gate is "ratio < 0.5
  in 20 steps", same as LoRA.
- `make verify-mirrors` clean. (CUDA file auto-generated by
  `prep/gen_cuda_mirror.rb`.)

## Risks

| Risk | Mitigation |
| --- | --- |
| Graph node count exceeds the 65K sched-hash budget once every weight has an opt_step | Re-measure on a real build; bump if needed (sched hash is uint slots, cheap). |
| GGUF copy primitives don't cover all of {token_embed, output, norm} when those are mmap'd in the existing path | We're skipping embeddings + final norm in the MVP, which sidesteps this. Add later if needed. |
| `tnn_pin_all_graph_b_nodes` (CPU sched-alias workaround) keeps too much alive | Likely OK at SmolLM2-135M; if memory pressure shows up we revisit per-graph instead of all-nodes pinning. |
| Adam state on CUDA + writable weights on CUDA + grads on CUDA — total VRAM | GB10 has 121 GB; 2 GB is trivial. Larger models (1.5B+) need a memory pass. |

## Update — 2026-05-21 (step 2)

### Embeddings + final-norm are now trainable (opt-in)

`enable_full_finetune_embeddings!` (default OFF) promotes
`token_embed`, the final-norm gamma, and the untied output projection
(if present) to writable F32 + Adam m/v + set_param + opt_step.
When off, they stay mmap'd / read-only and the rest of the model
still trains.

On SmolLM2-135M (vocab=49K) the on/off paths both converge identically
on the smoke (CE 9.24 → 0 in ~5 steps either way).

**Update — Qwen-vocab embed training now works** (vendor-patches/0006).
The CUDA kernel for `get_rows_back` launched with `gridDim.y = vocab`,
which exceeded the 65535 grid limit for V > 65K (Qwen2.5: V=151936 was
the canary). The patch chunks the launch: each call handles at most
65535 rows, and a `row_offset` parameter on the kernel positions the
chunk within the destination vocab axis. SmolLM2-135M (V=49K) needs
exactly one chunk and behaves identically. Qwen2.5-1.5B (V=152K) now
trains the full embedding: CE 17.65 → 0 over 2 steps.

Backend zero-init for big Adam tensors: a new `tnn_zero_tensor` C
primitive uses `ggml_backend_tensor_memset` so the 1 GB embedding
Adam state doesn't materialize a 233M-element Ruby Float array
first. Saves ~2 GB transient RAM and ~10 s of Ruby-side fill.

### F3 on a larger base — verified

`smollm2_seq_full_finetune_cuda` runs against `data/qwen25-1.5b-native.gguf`
with embeddings frozen (default). CE 17.65 → 0.0 within 2 steps —
the per-block parameter count (~1.3B trainable) saturates the
trivial uniform-target objective fast.

Memory at 1.5B per-block-only F32:
  base weights mmap   (read-only):  ~5 GB
  writable per-block weights:       ~5 GB
  gradients (autograd):             ~5 GB
  Adam m + Adam v:                 ~10 GB
  ----------------
  total                            ~25 GB

GB10's 121 GB swallows it easily.

## What still isn't done

- Q8 base for full FT. F4 (LoRA on Q8) ships; mixing Q8 base with
  full-FT updates needs its own code path.
- 3B / 7B full FT. The 25 GB scaling at 1.5B suggests 3B is ~50 GB
  (fits) and 7B is ~120 GB (doesn't — would need a memory pass).
