# E1 / E2 scope investigation

**Date:** 2026-05-27. **Status:** scope-and-decompose, not a commitment.
**Context:** Tao filed `toy#vit-support` (GH#13) and `toy#qwen-embedding-transfer`
(GH#14) as the two research-headline blockers. Both were `scope investigation
(defer)` in the local task list. This doc breaks each into actionable
sub-issues, identifies the cheapest first step for each, and flags the
real-cost items so we can stage the work honestly.

The Tao specs themselves (`tao/specs/E1-vit-pure-emb-n3.md`,
`E2-qwen-410m-1b.md`) carry the experiment design; this doc is purely
about toy-side capability gaps.

## E1 — ViT-Tiny (GH#13)

### What toy has

- Nothing image-related: no Conv2D, no patch embedding, no image loader.
- LayerNorm forward + backward (`tnn_layer_norm`, `tnn_layer_norm_back`).
- GELU forward (used in inference). Backward — not yet wired into a
  training graph but `ggml_gelu_back` exists upstream.
- AdamW (already used in `realize_for_random_init`).
- Cross-entropy loss + grad (for token classification — generalises
  trivially to image classification: it's CE over class logits).
- Cosine LR schedule — not yet; current example uses constant LR.

### What toy needs

Decomposed into sub-issues (effort = single-PR units):

1. **E1.1 — Conv2D + Im2Col FFI primitives** *(1–2 days)* ✅ **shipped 2026-05-27** (`a404d6d`)
   Wrap `ggml_im2col`, `ggml_im2col_back`, `ggml_conv_2d` in `tinynn.h`
   + `tnn_conv2d_*`, `tnn_im2col_*` helpers. Mat-roundtrip tests vs
   PyTorch. Per-head pattern: forward in `lib/llama_seq_forward_ffi.rb`
   wouldn't apply here — ViT lives in a new file.

2. **E1.2 — `patch_embed` op** *(0.5 day)*
   Compose conv2d(3→192, k=16, s=16) + transpose. Lives on top of E1.1.

3. **E1.3 — ViT forward + training graph** *(2 days)*
   New file `lib/vit_tiny_forward_ffi.rb`. Class token + learned pos
   embed (parameter tensors, no RoPE), 12 blocks of LayerNorm + MSA +
   MLP(GELU). MSA is attention without RoPE; MLP is gate-less. Mirror
   to CUDA/Metal via `gen_cuda_mirror.rb`.

4. **E1.4 — timm → GGUF weight extractor** *(0.5 day)*
   `prep/extract_vit_tiny.py` — loads `vit_tiny_patch16_224` IN-21k
   AugReg, writes a GGUF in toy's naming convention. Python script,
   not Ruby. Only `patch_embed.proj.{weight,bias}`, `pos_embed`,
   `cls_token` need to round-trip for E1.

5. **E1.5 — Image dataset loader** *(1 day)*
   Avoid binding libjpeg/libpng into Ruby — instead, ship a Python
   preprocessor (`prep/preprocess_images.py`) that decodes
   Flowers-102 / Stanford Cars / CIFAR images and dumps batches as raw
   `.bin` files (`[B, 3, 96, 96]` f32, normalised). Ruby loader is then
   `read_floats_from_disk` over the batch files. Cosine LR schedule
   lands here too.

6. **E1.6 — `examples/07_train_vit_tiny.rb`** *(0.5 day)*
   Wire E1.1–E1.5 into a `06`-style training entry point. Emits the
   frozen `toy/v1` events.jsonl. Acceptance: 200-step smoke on
   CIFAR-tiny without crashing, final loss < init loss.

**Total: 5.5–7 days**, plus integration + bug-hunt overhead. The image
loader (E1.5) is the place where surprises live — JPEG handling, value
range, augmentation pipeline; everything downstream is "use a primitive
we already wrote elsewhere in toy."

### Cheapest first step

**E1.1 (Conv2D + Im2Col FFI)** is pure C binding. It doesn't touch the
Ruby training graph at all — adds three functions to `tinynn.h`, three
implementations to `tinynn_ggml.c`, a smoke that round-trips a Mat
through a Conv2D op vs PyTorch. Lands in a single session, unlocks E1.2
+ E1.3.

## E2 — Qwen-2.5-1.5B → 410M (GH#14)

### What toy has

- Qwen-2.5 *inference* — yes (per README + multiple bench memories).
- Qwen-2.5 *training* — `realize_for_random_init` builds a SmolLM2-shape
  forward + backward graph (per-head GQA, SwiGLU, RoPE, RMSNorm). It's
  one config away from being Qwen-shape; the architecture is the same
  modulo width.
- AdamW + Adam moment tensors per param (just shipped: #11 puts
  semantic names on them).
- GGUF mmap loader with Q8/Q6/Q5 dequant — donor extract is two
  function calls away.
- Token embed lookup — yes. Tied embeddings — yes (per `cfg.tied_embedding`
  handling).

### What toy needs

Decomposed into sub-issues:

1. **E2.1 — Qwen-410M from-scratch smoke** *(0.5 day, cheapest)* ✅ **shipped 2026-05-27** (via GH#17 graph-capacity unblock; 24L × 16H trains)
   Verify `realize_for_random_init` accepts 24L × 1024 × heads=16, kv=2,
   d_ff=2816, ctx=2048 (the granite_transfer Qwen-shape config). Run
   `examples/06_train_from_scratch.rb` at that shape for 50 steps on
   CPU. If it works, the *target* arch is done — only the transfer
   pipeline + data loader remain.

2. **E2.2 — Donor extract from Qwen-2.5-1.5B** *(0.5 day)*
   Add `prep/extract_donor_embed.rb` that loads
   `Qwen2.5-1.5B-Instruct.gguf` with the existing mmap loader, copies
   `token_embd.weight` (151 936 × 1 536) to a standalone
   `donor_embed.gguf` (single tensor + minimal metadata). About 100
   lines.

3. **E2.3 — Trainable projection lens in forward graph** *(1 day)* ✅ **shipped 2026-05-27** (`0e31d4d`)
   Insert `Linear(1536, 1024)` after embedding lookup when
   `cfg.donor_d_in != nil`. Adds one PARAM tensor + one matmul to the
   graph. Backward already flows through matmul. New realize path:
   `realize_for_warm_start(cfg, donor_path, ...)` that loads the donor
   embed (frozen or trainable) + initialises the projection.

4. **E2.4 — Streaming text loader (corpus shim)** *(1.5 days)*
   FineWeb-Edu is large (~3 TB); we don't need the whole thing for
   smoke. Strategy: write `prep/pretokenize_corpus.rb` that takes a
   pre-downloaded FineWeb-Edu shard and writes packed token IDs to
   `.bin` files; Ruby loader is `next_batch_tokens(path, B, T)`.
   Network downloads stay out of Ruby. Cosine LR + AdamW config land
   here too.

5. **E2.5 — `examples/example_train_qwen_410m.rb`** *(0.5 day)*
   The driver. Honors `INIT=warm|scratch`, `TOKENS=...`,
   `SEED=...`. Emits frozen `toy/v1` events. Eval every 100 steps on a
   held-out shard.

6. **E2.6 — PCA init of projection lens** *(optional, 0.5–1 day)*
   For *fully faithful* reproduction of granite_transfer#38, the
   1536→1024 projection is PCA-init'd on donor activations. Without
   PCA, warm-trainable still converges but possibly slower. **Defer
   until we have a no-PCA baseline number to compare against.**

**Total: 3–4 days** without PCA, 4–5 with. E2 is materially easier than
E1 because we don't need a new operator — every primitive already
exists.

### Cheapest first step — done, surfaced one real blocker

Smoked `D_MODEL=1024 D_FF=2816 N_HEADS=16 N_LAYERS=24 CONTEXT=128 SEED=0`
on the existing CPU `realize_for_random_init`:

| Layers | n_heads | result |
| --- | --- | --- |
| 2 | 4 (SmolLM2-shape) | ✅ trains (baseline; 4e959ad) |
| 8 | 16 (Qwen-shape) | ✅ trains, CE 6.44 → 4.74 in 2 steps |
| 24 | 16 (Qwen-shape) | ❌ `GGML_ASSERT(cgraph->n_nodes < cgraph->size)` at `ggml.c:6938` during `tnn_build_backward` |

So the Qwen *architecture* compiles + trains under `realize_for_random_init`
— the only structural blocker we found is graph node capacity. The
session-level forward + backward graphs are allocated at 65536 in
`tinynn/tinynn_ggml.c:258` but the per-head-decomposed forward at 24L
× 16-head + its backward expansion exceeds that. Per-head decomposition
multiplies node count by `n_heads`, so the cap scales as
`O(n_layers × n_heads)` and we cross 65536 between 8L and 24L.

**New sub-issue E2.0** (precedes E2.1): bump or dynamically size the
session compute-graph capacity. Two options:

- *Cheap*: bump to 262144 (4×). Cost: one int per slot in the graph
  header (negligible).
- *Right*: size the graph capacity from the realize call — pass
  `n_layers × n_heads × per_layer_const` from Ruby into `tnn_session_init`
  or a new `tnn_set_graph_capacity` helper.

The cheap option unblocks E2.1 immediately. The right option is a
prereq for actually pushing toy to larger architectures (and it's
small — ~30 lines). Recommend the right option.

## Risk + open questions

- **CUDA training at this scale.** `realize_for_random_init` is
  CPU-only today (#152). E1 + E2 both need CUDA training for their
  acceptance criteria (E1 spec says `device: cuda`; E2 spec same).
  So #152 is on the critical path. It's already filed; doing E1 / E2
  before #152 means CPU-only smokes only.

- **Image loader path.** For E1, decoding JPEG/PNG in Ruby is a hassle
  we don't want. The Python preprocessor approach (E1.5) sidesteps
  this but means E1 has a small Python dependency in `prep/`.

- **FineWeb-Edu access.** For E2, we need ~10 M tokens of FineWeb-Edu
  pre-downloaded to disk (for the 10 M-token smoke acceptance). That's
  ~50 MB of pretokenized data. Not a blocker but not free either.

- **PyTorch parity tests.** For Conv2D (E1.1), the standard sanity
  check is a Mat round-trip against PyTorch's `nn.Conv2d`. We have the
  infra (`tinynn/bench_vs_pytorch_*`); it's just labour to add a
  conv2d case.
