## Approach — code generation, not module-include

The original Phase 0.6 doc proposed a `TransformerLMGraph` module
that both `SmolLM2KVFFICache` and `SmolLM2KVFFICacheCuda` would
`include`. That assumes Spinel resolves instance-method dispatch
on includes correctly across modules — uncertain.

The pragmatic alternative: **the CPU file is the source of truth;
the CUDA file is auto-generated by mechanical substitution.** Both
files stay committed (for `git blame`, reviewer eyes, and CI of
the CUDA compile path), but only one is edited by hand.

`prep/gen_cuda_mirror.rb` does the substitution: class names,
`TinyNN` → `TinyNNCuda`, backend selector `(0)` → `(1)`, file
header. `make verify-mirrors` re-runs the generator in `--verify`
mode and exits non-zero if the on-disk CUDA file has drifted.

For files with real CPU-only blocks (the trace-tap diagnostics on
`SmolLM2KVFFICache`, for example), the generator honors sentinel
comments:

```ruby
# CUDA-MIRROR-SKIP-BEGIN: trace-tap is CPU-only
@trace_on = false
...
# CUDA-MIRROR-SKIP-END
```

No `CUDA-ONLY-INSERT` sentinel yet because no CUDA file has
content the CPU version lacks. (When it does, we'll add one.)

Step 2 exercises the STUB sentinel. The CPU file's trace-tap surface
(`enable_trace!`, `trace_tap`, `dump_trace`, the trace ivars, the
inline `trace_tap(...)` calls scattered through `build_decode_step`)
is replaced on the CUDA side with three no-op stubs:

```ruby
def enable_trace!; end
def trace_tap(_name, t); t; end
def dump_trace; end
```

The inline calls collapse to identity at trace-off (the only mode
the CUDA mirror knows). One small CPU-side simplification fell out
of step 2 as well: `TinyNN.stage_row_major_and_upload(...)` becomes
`TinyNN.upload_row_major(...)`, since the latter exists on both
backends and the mechanical rename then works. Same change as in
step 1's seq pair.

## Re-trigger conditions for the deferral

(Kept for posterity — all of these became history when re-trigger #1
fired.)

1. **A new architecture lands and needs > ~50 LOC of CPU/CUDA mirror
   duplication.** ✅ M3 fired this.
2. **A CPU/CUDA divergence ships to production.** Still possible,
   would now be caught by `make verify-mirrors`.
3. **The Spinel ivar-collision (#626 issue #1) is upstream-fixed.**
   No longer load-bearing — the `@seq_*` prefix discipline plus the
   distinct-class-names rule sidesteps it entirely.

## What still needs to migrate

The older KV-cache pair is ~1800 LOC of duplicated code. Migration
plan:

1. Update `prep/gen_cuda_mirror.rb`'s substitution table to cover
   the SmolLM2KV* class names.
2. Add `CUDA-MIRROR-SKIP-BEGIN/END` sentinels around CPU-only
   blocks on the CPU file:
   - `@trace_on` / `@trace_names` / `@trace_tensors` ivars + their
     init lines.
   - `trace_tap` method.
   - `dump_trace` method.
   - (anything else found at verify time)
3. Run `make gen-mirrors` to produce the CUDA mirror.
4. Run the full `*_cuda` smoke set; bit-identical bench parity is
   the gate.
5. Commit; remove the manual mirror discipline from the file
   headers.

`lib/gpt2_ffi*.rb` (FullForwardFFICache, the GPT-2 single-step path)
hasn't had a CUDA mirror exercise this work. When/if it grows one,
the generator already supports it — just extend `MIRRORABLE`.

## What replaces the deferred state

- `make verify-mirrors` runs in seconds; cheap to wire into any
  pre-push hook.
- The CPU file IS the source. No more "edit both" review burden
  for the migrated pairs.
- The substitution table is small and reviewable — additions
  require thinking about whether the rename is mechanical or
  needs a SKIP sentinel.

Phase 0.6 isn't a one-shot refactor anymore; it's an ongoing
discipline. Each new pair that lands picks up the generator on the
next pass.
