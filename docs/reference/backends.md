# Backends

Toy runs on three compute backends, all via [ggml](https://github.com/ggml-org/ggml):

| Backend | CLI default | Where | Mirror suffix |
| --- | --- | --- | --- |
| CPU (ggml-cpu) | yes | everywhere | — |
| CUDA (ggml-cuda) | opt-in | GB10 sm_121 | `_cuda` |
| Metal (ggml-metal) | opt-in | Apple Silicon | `_metal` |

The five-layer algorithms (`lib/toy/llm/`) carry `_cuda` / `_metal` mirrors for
L1/L2/L3, generated by `prep/gen_cuda_mirror.rb` from `MIRRORABLE` markers and
gated bit-identical by `make verify-mirrors`. This document covers the FFI bridge
those layers dispatch through, the performance yardstick, and the open
backend/scale research directions.

CPU is the only backend wired into the CLI today; GPU runners (`--device`) are a
deferred direction (see [roadmap](../roadmap.md)).

## The tinynn FFI bridge

`tinynn/` is a thin C shim — an opaque-handle wrapper over ggml — that lets
Spinel-compiled Ruby dispatch its hot matrix operations through ggml on CPU,
CUDA, or Metal. The Ruby side lives in:

| File | Module / class | Backend |
| --- | --- | --- |
| `lib/toy/ffi/tinynn.rb` | `TinyNN` | CPU |
| `lib/toy/ffi/tinynn_cuda.rb` | `TinyNNCuda` | CUDA |
| `lib/toy/ffi/tinynn_metal.rb` | `TinyNNMetal` | Metal |

The C shim (`tinynn/tinynn_ggml.{c,h}`, `tinynn/tinynn_gguf.{c,h}`) compiles into
`tinynn/libtinynn_ggml.a` (CPU) and `tinynn/libtinynn_ggml_cuda.a` (CUDA). The
separate module names let all backends co-exist in one Spinel translation unit
without colliding.

### Op coverage

The same op surface is verified parity on CPU and CUDA. Parity smokes live in
`tinynn/ab_smoke_*.rb`; the consolidated CUDA driver is
`tinynn/ab_smoke_all_cuda.rb`.

| Op | CPU | CUDA | Notes |
| --- | --- | --- | --- |
| `matmul(a, b)` (A·B) | yes | yes | A·Bᵀ via b-transposed upload |
| `matmul_t(a, b)` (A·Bᵀ) | yes | yes | ggml-native |
| `t_matmul(a, b)` (Aᵀ·B) | yes | yes | both inputs uploaded transposed |
| `add(a, b)` | yes | yes | element-wise |
| `gelu(a)` | yes | yes | tanh approx, matches feed_forward |
| `rms_norm(x, γ, ε)` | yes | yes | last-dim norm + γ broadcast |
| `softmax(a)` | yes | yes | per-row along ne[0] |
| `scale(a, s)` | yes | yes | a × scalar |
| `embed_lookup(tab, idx)` | yes | yes | gather rows |
| `embed_back(d_out, idx, V)` | yes | yes | scatter-add (accumulates duplicates) |
| `softmax_back(a_soft, dy)` | yes | yes | `ggml_soft_max_ext_back` |
| `gelu_back(x, dh)` | yes | yes | custom kernel (no ggml op exists) |
| `cross_entropy_grad` | yes | yes | composed: softmax + scale + add + one-hot |
| `sgd_step(p, g, lr)` | yes | yes | composed: `add(p, scale(g, -lr))` |
| `adam_step(...)` | yes | yes | custom kernel (sqrt + div) |
| `opt_step_adamw(...)` | yes | yes | ggml-native AdamW, in-place update |

The KV-decode path adds `silu`, `mul`, `rope_ext`, and i32 input primitives;
SwiGLU is `silu(gate(x)) ⊙ up(x) · W_down` chained in one graph, and GQA reuses
each KV head across its query group via per-Q-head matmul against shared K/V
buffers.

Two ops stay CPU-only: the `gelu_back` and `adam_step` custom kernels run on the
session's host scratch buffer regardless of backend (inference never touches
them). K-quant dequant (Q4_K/Q5_K/Q6_K) is not wrapped through the bridge —
legacy quantizers (Q8_0, Q4_0, Q5_0) work via load-time `to_float` traits.

### Persistent-session vs one-shot API

**One-shot** wrappers (`TinyNN.matmul`, `.add`, …) spin up a fresh ggml graph,
run the op, and tear it down. Convenient for ad-hoc tests, but slow for hot
loops — per-call `ggml_init` + scheduler-alloc dominates the math, and the FFI
boundary is ~800 µs/call regardless of shape. The 38× FFI win is a whole-graph
effect, never a per-op one.

**Persistent-session** is the production path: build a graph once, run it many
times.

```ruby
sess = TinyNN.persistent_new(0)               # 0 = CPU, 1 = CUDA
ta   = TinyNN.alloc_2d(sess, T, D)            # input slot
tw   = TinyNN.alloc_2d(sess, D_out, D)        # weight slot (uploaded transposed)
tc   = TinyNN.build_matmul(sess, ta, tw)      # op tree
TinyNN.realize(sess, tc)                       # allocate all backend buffers

TinyNN.upload_transposed(sess, tw, w_mat)      # upload weights ONCE
loop do
  TinyNN.upload_row_major(sess, ta, input_mat)
  TinyNN.compute(sess)
  output = TinyNN.download_matmul(sess, tc, T, D_out)
end
TinyNN.persistent_free(sess)
```

Mixing several `build_*` calls before `realize` builds a multi-op graph that
runs as one ggml dispatch. The seq-forward builders
(`lib/toy/llm/engine/llama_seq_engine.rb` + `_cuda` / `_metal`) realize the whole
forward — and the training backward — as one persistent graph: weights live in
a `ctx_w` context uploaded once, and per step only `token_ids` cross the FFI
boundary.

### `tnn_engine` vs `tnn_session`

The C shim caches one `tnn_engine` per backend flavour (backend objects +
scheduler, one each for CPU/CUDA across the whole process). `tnn_session_new`
allocates a fresh `ggml_context` + `cgraph` + scratch buffer and references the
cached engine. A session is realized once; `tnn_compute` runs many times against
the same realized graph.

### Shape conventions

Project `Mat` is row-major: `flat[i * ncols + j]` is element `(i, j)`. ggml
stores 2-D tensors with `ne[0]` as the fastest stride and `ne[1]` slower, so a
`Mat(rows, cols)` becomes a ggml tensor with `ne[0] = cols, ne[1] = rows`.

`ggml_mul_mat(A, B)` computes `A · Bᵀ`. To get a plain `A · B`, upload `B`
transposed (`upload_transposed`). The result then carries `ne[0]` = output rows
and `ne[1]` = output cols, which is why `download_matmul` reads it back as
`scratch[j*m + i]`.

### Scratch-buffer hardening

Each session owns a 16 MiB host-side scratch buffer (4 M f32 slots, reused as
i32 for integer primitives). Bulk uploads memcpy directly from `Mat.flat`'s
contiguous f64 storage via Spinel's `:float_array` / `:int_array` specs — no
per-element FFI calls.

Tensors larger than 16 MiB must use the chunked uploaders
(`tnn_upload_from_float_array` for f32, `tnn_upload_transposed_f64` for
transposed f64). The hardened primitives fail loud rather than silent:

| Primitive | Out-of-range behaviour |
| --- | --- |
| `tnn_scratch_set` / `_i32` | warn once per session; skip the write |
| `tnn_scratch_get` / `_i32` | warn once per session; return 0 |
| `tnn_upload` | warn once; return −2; do not memcpy |
| `tnn_download` | warn once; return −2; do not memcpy |

This replaced silent UB (`memcpy` past the scratch end into adjacent heap) — the
canonical motivating bug was a 17.4 MB `ffn_gate` overflow at >16 MiB.
`TNN_ASSERT(cond, msg)` from `tinynn/tinynn_ggml.h` guards "shouldn't happen"
boundaries; it compiles away under `-DNDEBUG`.

### FFI trace tap

The seq-forward caches carry a zero-cost numerical trace tap for pinning down a
diverging layer when a new model produces NaNs or gibberish:

```ruby
kv.enable_trace!                 # off by default; one-line opt-in
# ... decode a step ...
kv.dump_trace                    # prints min/max/|mean|/nan per labelled tap
```

With tracing off, `trace_tap(name, tensor)` just returns its tensor — a single
boolean branch, no graph change, unmeasurable in benchmarks. With it on, the tap
also calls `tnn_set_output` so the scheduler keeps the tensor's buffer alive past
`compute`; `dump_trace` then downloads each tap and runs the stats reductions
(`tnn_scratch_min_f32`, …) in C, one FFI call per stat. The tap is
value-transparent — it returns the same handle it received, so it composes
anywhere in a graph builder without changing topology.

For direct GGUF→ggml streaming (4 B/param, no Mat round-trip) and the
`read_persistent_mat` inspection primitive, see
[loader-api.md](loader-api.md).

## Performance yardstick: toy vs PyTorch

PyTorch is mature and well-optimised; toy does not try to beat it. It is used as
a fixed "old-stable" reference to keep toy's defaults honest. The gate is the
**ratio** (toy ÷ PyTorch), not absolute milliseconds — absolute step time is
machine- and thermal-dependent, the ratio is portable, and the signal we care
about is "is the gap to old-stable reasonable, and is it widening?"

```sh
# On gx10 (where both engines live):
make bench-vs-pytorch          # measure both live, gate the ratio
make bench-vs-pytorch-update   # re-record the budget after an intended change
make bench-vs-pytorch-report   # measure + print, no gate
```

Both engines are always measured **live, same session** — never against a stale
figure.

### What it measures

The same model on both sides — a Llama at SmolLM2-135M dims — across two
workloads that exercise toy's real code paths:

- **train** — one full fine-tune step (forward + cross-entropy + backward +
  AdamW), T=4, batch=1. Matches `demos/seq_train_bench_cuda MODE=ft`.
- **infer** — KV-cache greedy decode, batch=1, one token/step, prefill + warmup
  excluded. Matches `demos/qwen25_bench_cuda`.

The PyTorch side runs `transformers`' `LlamaForCausalLM` with random weights
(throughput is weight-independent, so no checkpoint or tokenizer to match) — a
faithful Llama (RMSNorm / RoPE / GQA / SwiGLU / KV-cache), not an approximation.

### How it's wired (two environments)

On gx10 the two engines live in different places and the orchestrator bridges
them:

- **toy CUDA** runs **natively** on the gx10 host (Spinel binaries +
  `tinynn/libtinynn_ggml_cuda.a`). The orchestrator runs the `demos/*_cuda`
  binaries and parses their output.
- **PyTorch** runs in the **`gx10/dev-pytorch` container** (it has `torch` +
  `transformers`; the host does not), invoked via `docker run`.

That container invocation is the only environment-specific knob, isolated in one
env var (`PT_CMD`). Everything else is engine-agnostic. Toy has no
`docker-compose.yml`, so `gx-run` is not used for the toy side.

### Files

| File | Role |
| --- | --- |
| [`bench/ref_pytorch.py`](../../bench/ref_pytorch.py) | The PyTorch yardstick. `--workload train\|infer\|both`, `--device cuda\|cpu\|mps`. Emits `BENCH pt_*` lines. |
| [`bench/check_vs_pytorch.rb`](../../bench/check_vs_pytorch.rb) | Orchestrator. Runs both engines, computes `ratio_*_toy_over_pt`, soft-gates against the budget. `--update` / `--report`. |
| [`bench/baselines_vs_pytorch.csv`](../../bench/baselines_vs_pytorch.csv) | The ratio budget (`metric,value,unit,direction,tolerance_pct`). `direction=lower`; the bench fails only if a ratio grows more than `tolerance_pct` past its recorded budget. |

This mirrors the local `make bench` machinery (BENCH lines → CSV → per-metric
tolerance), so there is one mental model for both. A ratio of `1.0×` is parity;
`1.38×` means toy is 38 % slower on that workload.

### GB10 numbers

Latest GB10 light gate (SmolLM2-135M, measured live):

| Workload | toy (CUDA) | PyTorch (CUDA) | ratio toy/pt |
| --- | --- | --- | --- |
| Full-FT training step (T=4) | ~77 ms | ~77 ms | **~1.0× (parity)** |
| KV-cache decode | ~82 tok/s | ~113 tok/s | **~1.38×** |

### Heavy mode

The light gate runs in well under a minute and is meant to fire on every
meaningful commit. A heavy variant exercises the libs at real scale — the
pressure you want when choosing between optimization strategies.

```sh
make bench-heavy                # toy-only gate vs bench/baselines_heavy.csv
make bench-heavy-report         # measure + print, no gate
make bench-vs-pytorch-heavy     # adds the PyTorch ratio gate (needs docker image)
```

Two workloads, shared between the toy-only and ratio targets so they cannot
drift:

- **`heavy_train_lora_1p5b`** — LoRA-Q step on Qwen2.5-1.5B, seq=256, 8 steps
  after warmup. Emits `step_ms_{mean,p95,stddev}`.
- **`heavy_infer_7b_q8`** — KV-cache decode on Qwen2.5-7B-Q8 with
  `KV_Q8=1 FLASH_ATTN=1`, prefill=512, n_new=128. Exercises the mmap + Q8
  dequant + opt-in perf knobs at real model size.

| Workload | toy | PyTorch | ratio toy/pt |
| --- | --- | --- | --- |
| LoRA-Q step, Qwen2.5-1.5B seq=256 | ~240 ms | ~120 ms | **~2.01×** |
| Decode, Qwen2.5-7B-Q8 (KV_Q8+FLASH) | ~12.7 tok/s | ~7.6 tok/s | **toy wins** |

The 7B comparison is toy-Q8 vs PT-F32 — the real-world comparison, since Q8 is
how toy users actually serve 7B, and decode is bandwidth-bound so 4× fewer
weight bytes pays off. The ~2× training gap is fair (both F32) and attributable
to upstream ggml-cuda single-stream serialization, **not** application-layer
overhead (see
[upstream issue 05](../archive/upstream/issues-vendor/05-ggml-cuda-stream-overlap.md)).

### Caveats

- **Small models on CPU**: at ≤135M, toy's ggml-CPU path can *beat* CUDA (CUDA's
  per-step launch overhead dominates tiny matmuls; crossover ≈ d_model 896). So
  "use the GPU" is not automatically the reasonable default at small sizes.
- **CPU gap is larger (~2×)**: where matmuls are tiny, toy's per-head attention
  decomposition (separate GEMMs + concat per head, vs a fused QKV) costs more
  relative to kernel time. On the GPU at 135M this matters less — hence parity on
  train.

## Future directions

These are live research notes, not commitments. The full deferred list lives in
[roadmap.md](../roadmap.md); this section keeps the backend-and-scale rationale
close to the code it touches.

### Single-machine training maturity (the real near-term work)

The open multi-GPU issues (#3/#4/#5) implicitly assume a mature single-machine
training story that does not fully exist yet. The cheapest-with-most-value
prerequisites — each independently useful regardless of any parallelism
decision:

- **Batched training input (B>1)** — today the seq-forward builders realize input
  shape `[T, 1]`. Generalising to `[T, B]` (input, labels, mask, RoPE, mean-over-
  batch loss) across the CPU/CUDA/Metal builders is ~100-200 LOC, and lifts even
  single-GPU throughput via better matmul utilization. This is the gating
  prerequisite for data-parallel training.
- **Gradient accumulation** — accumulate across N micro-batches before the
  optimizer step; ~20 LOC in the Ruby train loop (skip `OPT_STEP_ADAMW` until the
  Nth iter). Effective batch = micro_batch × accum_steps without the big-batch
  memory cost.
- **Mixed precision (bf16/f16)** — weights/activations in bf16 with an f32 master
  copy for AdamW state. ggml already supports `GGML_TYPE_BF16`/`F16`; training
  would need `realize_for_random_init` to accept a target dtype. Memory halves,
  throughput typically improves 1.3-1.5× on tensor-core hardware.
- **Activation recomputation (gradient checkpointing)** — drop intermediates on
  forward, recompute on backward; halves activation memory at ~30 % compute. Self-
  contained, no multi-GPU plumbing needed.

### Multi-GPU modes

- **Mode 1 (replicate inference)** — one session pinned per device, N independent
  replicas. Smallest lift; device-selection plumbing is the only blocker.
- **Mode 2 (layer split)** — split one model across N GPUs via ggml-sched's
  multi-backend array. Buys *capacity* (model fits), not throughput.
- **Mode 3 (DP training)** — data-parallel across replicas. Honest dependency
  chain: **batching → DP → multi-node.**

For DP, **ZeRO-1** optimizer-state sharding (each replica holds 1/N of the AdamW
state, all-gather updated weight slices per step) is mostly an optimizer-loop
rewrite once DP lands; ZeRO-2/3 need deeper graph changes. **CPU offload**
(ZeRO-Offload style: `m`/`v` Adam tensors on the CPU backend, apply AdamW on host)
roughly halves GPU memory pressure and reuses the cross-backend `cpy`-routing the
BYO-pointer mmap already exercises — useful only at ≥1B params toy does not yet
target.

For multi-node transport, **NCCL** is the obvious choice for gx10-class hardware
(small C FFI wrapper + a rank-exchange bootstrap), **GLOO** the fallback for
heterogeneous topologies. Sockets aren't worth implementing for production DP.

The strategic tension is whether toy should own distributed training at all, or
do excellent single-GPU (+ mode-1/2) training and delegate large-scale DP to an
external orchestrator. The most coherent path: earn the single-machine
prerequisites first (they have value either way), then decide on multi-GPU based
on what hardware shows up.

### Beating PyTorch on training (backend landscape)

ggml-cuda's three training limits cap toy short of compiled PyTorch on the
"everything fuses" shapes:

1. **Backward gaps in vendored ops** ([ggml#1514](https://github.com/ggml-org/ggml/issues/1514)):
   `GGML_OP_NORM` (LayerNorm), `GGML_UNARY_OP_GELU`, and `ggml_conv_2d` have no
   usable auto-backward. Toy works around with RMSNorm + SiLU + flat-linear
   patch_embed; vanilla LayerNorm+GELU arches (GPT-2, BERT, ViT-Tiny) can't train
   through ggml-cuda today.
2. **Per-op kernel launch dominates at small shapes** — ~800 µs/op even via the
   persistent session at toy widths.
3. **Single-stream dispatch** — ggml-cuda computes a graph on one stream; modern
   stacks overlap memcpy + compute + prefetch. Filed upstream as
   [issue 05](../archive/upstream/issues-vendor/05-ggml-cuda-stream-overlap.md);
   nothing toy can close from its side.

Where toy *can* plausibly win on single-GPU fixed-shape small-to-medium models:
no Python interpreter loop (AOT'd via Spinel), no per-forward autograd-tape
allocation (graph realized once, reused), kernel picked at realize time, fixed
shapes. Realistic claim: 1.2-2× over eager-PyTorch per step, roughly matching
warmed `torch.compile`.

The staged plan, only after batching lands:

1. **Stage 1 — measure** which ops actually hurt (per-op attribution on toy's
   real workloads). Anything <5 % isn't worth optimizing.
2. **Stage 2 — libtorch matmul behind the same `tnn_matmul`**, A/B'd on the
   canonical shape. Proceed only if libtorch wins ≥20 %.
3. **Stage 3 — backend selector** on `tnn_session_new(backend_kind)`: existing
   ggml backends become 0/1/2, libtorch becomes 3.
4. **Stage 4 — Triton-AOT** kernels (build-time compile to `.cubin`) for fused
   ops ggml can't do well (QKV-fused attention, fused AdamW). This is where toy
   plausibly beats Inductor — fused kernels for *our specific shapes*.

The clean multi-backend shape is option 2: a parallel `tinynn_<backend>`
primitive table picked at session-new time, mirroring the existing
`tinynn` / `tinynn_cuda` / `tinynn_metal` split — the leaf ops differ, the graph
composition stays the same. The hard part is that the training graph embeds
backend assumptions (persistent-session lifetimes, per-head decomposition); a
non-ggml backend needs a thin abstraction over the persistent-tensor allocation
model. Skipped: hand-rolled cuBLASLt (enormous surface) and MLX (Mac is for fast
iteration, not production training).

### Decoupled / DiLoCo — heterogeneous co-training

The "start on a local machine, have a beefier CUDA host join mid-run" dream maps
onto the **DiLoCo** family (two-level optimizer: each replica trains its full
model independently for H inner steps, then exchanges pseudo-gradients for an
outer Nesterov-SGD step — orders of magnitude less communication than DDP).
Decoupled DiLoCo (DeepMind, 2026) adds a central synchronizer, K=1 quorum (one
learner can drive progress alone), and learner-recovery — structurally a good
fit for join-mid-training.

The compute-gap envelope matters: GB10 → 8×5090 (~5-10×) is genuinely
heterogeneous co-training; M3-Max → 8×5090 (~30-60×) is "the laptop participates
symbolically." Tiered plan, smallest primitive first:

- **Tier 1 — single-host, two-process, sync DiLoCo via file-swap.** Two train
  processes, different seeds; a coordinator averages weights via the outer step
  and both reload. Validates the algorithm against toy's checkpoint plumbing.
- **Tier 2 — two-host sync DiLoCo over a TCP socket.** Exchange flat f32/bf16
  deltas once per ~H steps; rendezvous = config file. A 100M model is ~400 MB
  exchanged every ~500 steps — trivial over Tailscale.
- **Tier 3 — async / late-join.** Membership protocol, per-learner inner-step
  scaling, staleness handling, reconnect/resume.

Gating dependencies, ranked: (1) **batching** — a batch=1 replica isn't a serious
contributor; (2) **numerical consistency** — the CPU/CUDA training divergence
(masked today by `tnn_pin_all_graph_b_nodes` in `lib/toy/llm/engine/llama_seq_engine.rb`)
must be root-caused first, or the outer step compounds diverging pseudo-gradients;
(3) transport (sockets suffice); (4) membership (~100 LOC); (5) async/staleness.
Toy's `runs/<id>/events.jsonl` and gradient sentinels are a real head start for
tracking inter-replica state. Worth an ablation before plumbing: DiLoCo's
empirical sweet spot is ≥400M params on long runs, exactly where toy's typical
small-model short-run profile is weakest.
