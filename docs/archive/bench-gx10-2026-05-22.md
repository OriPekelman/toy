# Bench snapshot — gx10, 2026-05-22

Pre-v0.1 perf check. Hardware: NVIDIA GB10 (Grace Blackwell), 121 GiB
unified memory, sm_121, CUDA 13.0. CPU: ggml-cpu with SIMD on aarch64.

Run via `demos/qwen25_bench_{cpu,cuda}` and `demos/seq_train_bench_cuda`.

## Inference — KV-cache decode (existing path)

PREFILL_T=32, N_NEW=8 generation tokens, warm cache (drop first 2).

| Model               | CPU tok/s | CUDA tok/s | CUDA / CPU |
| ------------------- | --------- | ---------- | ---------- |
| SmolLM2-135M F32    | **88.4**  | 75.5       | 0.85×      |
| Qwen2.5-0.5B F32    | 34.1      | **41.0**   | 1.20×      |
| Qwen2.5-1.5B F32    | 13.5      | **20.0**   | 1.48×      |
| Qwen2.5-7B Q8       | 4.2       | **13.6**   | 3.25×      |

**Reading.** CPU is the fastest path for SmolLM2-135M — ggml-cpu's
SIMD matmul beats CUDA's per-step kernel-launch overhead at small
hidden sizes. Crossover at d_model ≥ 896. CUDA gets a clean 3× at
7B-Q8 where the matmul cost dominates.

Versus the prior baseline (`archive/bench-gx10-2026-05-20.md`):
- Qwen2.5-1.5B F32 CPU: 6.4 → **13.5 tok/s** (2.1×). The bigger
  scheduler hash-set (16K → 65K) and the recent CPU-mirror dedup
  didn't directly speed inference; the win is likely from a smaller
  set of refactor side-effects (less Mat-allocation churn in graph
  build). Track in a follow-up if it matters.
- Qwen2.5-7B Q8 CPU: 2.4 → **4.2 tok/s** (1.75×).

No regressions detected.

## Sequence-mode training — step time (CUDA)

SmolLM2-135M F32 base, T=4 positions, 10 steps measured (first step
dropped as warmup):

| Mode          | step time (mean) | steps/sec | comments |
| ------------- | ---------------- | --------- | -------- |
| LoRA-Q r=8    | 108.0 ms         | 9.3       | ~540 adapter tensors trained |
| Full FT       | 108.5 ms         | 9.2       | ~600 weight tensors trained |

**Reading.** Full FT has essentially the same per-step cost as LoRA
on a 135M model. The opt_step nodes are cheap; the forward + backward
matmul kernels dominate. Real-SFT pacing — 1000 examples × 5 epochs
× 10 steps/sec ≈ 9 minutes of GPU. Practical.

## Memory — full FT footprint (1.5B)

`demos/smollm2_seq_full_finetune_cuda` against `qwen25-1.5b-native.gguf`
with embeddings frozen (default):

```
base weights mmap  (read-only):   ~5 GB
writable per-block weights:       ~5 GB
gradients (autograd):             ~5 GB
Adam m + Adam v:                 ~10 GB
-----------------------------------------
total                            ~25 GB
```

With embeddings on (`EMBED=1`), add ~3.7 GB for the 233M-element
(V=152K × d=1536) token-embed table × {weight, grad, m, v}. Still
fits with margin on the 121 GB unified-memory budget.

## What changed since 2026-05-20

| Area | Then | Now |
|---|---|---|
| Mirror dedup | Hand-mirrored | CPU = source, CUDA generated (Phase 0.6) |
| F2 LoRA      | KV-decode single-pos | M3 seq-mode multi-pos in one forward |
| F3 full FT   | Not built | Up to 1.5B verified |
| F4 QLoRA     | Not built | CPU + CUDA both ship |
| Qwen-vocab embed gradient | n/a | vendor-patches/0006 chunks `get_rows_back` past gridDim.y limit |

## Headroom (low-hanging items, not pursued in this snapshot)

- ggml-cpu doesn't pre-fetch the next layer's weights during the
  current layer's compute. On SmolLM2-135M each layer is small enough
  that the inner-loop dominates; on larger models the streaming
  read pattern might benefit from explicit prefetch hints. Defer.
- CUDA training step at T=4 is launch-bound for small models; T=16
  or T=32 should amortize. We haven't measured T-scaling.
- The `tnn_pin_all_graph_b_nodes` workaround for CPU sched-aliasing
  keeps every backward node alive. For 7B-scale models that's
  significant memory; a less blunt fix (pin only the problematic
  nodes) is a real follow-up.

No regressions to chase. Inference is healthy across the board;
training shape is fast enough to do real SFT inside an hour for
SmolLM2-class models.
