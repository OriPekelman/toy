## Patterns

### Memory: Phase 2 mmap holds across every native model

RSS ≈ GGUF file size for native-layout models. The 7B-Q8 case ran
at 7.1 GB CPU / 9.6 GB CUDA — still well under the legacy 19 GB
peak from before Phase 2.

### Q8 is ~1.4-2× faster than F32 on CPU

Memory-bandwidth-bound: less data per step → faster. Holds across
every size we tested.

### Legacy load is expensive — and re-converting fixes it

The four legacy-layout models (SmolLM2-135M/360M, TinyLlama-1.1B,
Llama-3.2-1B) were re-converted later the same day with
`--ggml-native`. Big wins across the board:

| Model            | Before (legacy) | After (native) | Speedup |
| ---------------- | --------------- | -------------- | ------- |
| SmolLM2-135M     | 9.88 tok/s      | **47.06**      | 4.8×    |
| SmolLM2-360M     | 3.69 tok/s      | **24.24**      | 6.6×    |
| TinyLlama-1.1B   | 1.09 tok/s      | **9.64**       | 8.8×    |
| Llama-3.2-1B     | 0.82 tok/s      | **7.14**       | 8.7×    |

The legacy path's Mat-mediated weight upload dominated wall time;
the native path mmaps weights directly with zero-copy via the
Phase 2 BYO-pointer code. Memory dropped proportionally too.

### CUDA-vs-CPU crossover at 7B

For ≤ 3B models, **CPU beats CUDA** in this benchmark — the
per-step graph rebuild dominates. CUDA wins decisively only at the
7B-Q8 Mistral case (2.52 s vs 3.34 s). Per-token amortization with
a longer N_NEW would shift this further toward CUDA.

The persistent-session refactor noted in
`[[project_persistent_bench_2026_05_14]]` already moved CUDA from
"4.5× faster than one-shot" but the per-step graph rebuild is
still real overhead. A future cgraph-cache could close this further.

### CUDA Q8 has known holes

Qwen2.5-1.5B-Q8 and -3B-Q8 abort (exit 134) on CUDA. 7B-Q8 and
Mistral-7B-Q8 (also Q8) succeed. The divergence is documented in
`docs/design/arch-struct.md` and the header of
`lib/toy_smollm2_ffi_kv_cuda.rb`: the CUDA decode_step has the
PRE-Phase-3 V-matmul order. F32 happens to land on a matmul shape
the CUDA kernel handles either way; Q8 with these specific
dimensions hits the broken path.

## Caveats for re-running on a clean machine

- Wall-clock includes load time. Per-token steady-state would be a
  more useful number — but harder to measure without instrumenting
  the demo. Phase A or later.
- The 8-token sample size is too small for stable tok/s — variance
  on consecutive runs is ±15-20%.
- We don't currently report TTFT (time-to-first-token) separately.
  Worth adding when this becomes a real bench harness.

## What changed vs the 2026-05-19 bench

Through `ToyLM` (the new code path) on a quieter machine:

| Comparison | 2026-05-19 (noisy) | 2026-05-20 (idle) |
| --- | --- | --- |
| Qwen2.5-7B-Q8 CPU       | 0.63 tok/s | 2.35 tok/s — **3.7× from less GPU contention** |
| Qwen2.5-3B-F32 CPU      | 0.63 tok/s | 3.65 tok/s — same factor |
| Qwen2.5-1.5B-Q8 CPU     | 4.71 tok/s | 8.99 tok/s — ~2× |

The earlier benchmark was running alongside a pt_data_worker job
at 95% GPU. Even though the GPU wasn't competing with the CPU
path directly, the system as a whole was busier (page-cache
contention, scheduler pressure). Clean-machine numbers are
~2-4× better at every size.
