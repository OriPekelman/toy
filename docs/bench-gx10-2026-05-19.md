# Bench gx10 — 2026-05-19

**Preliminary, noisy machine.** Run alongside an unrelated heavy
PyTorch training job (`pt_data_worker` at 95% GPU). CPU has 90 GiB
free of 121 GiB; CUDA was tabled. Real benchmarks need a clean
machine. This is for an "initial sense" only.

## Inference (CPU, Phase 2 mmap path)

All measured wall-clock for **8-token generation after a 5-token
prefill**. Realize+mmap is < 12 ms in every case (negligible). RSS
is peak process resident set, includes the mmap'd weight pages.

| Model            | Quant | RSS (GB) | Wall (s) | tok/s |
| ---------------- | ----- | -------- | -------- | ----- |
| Qwen2.5-0.5B     | F32   | 1.9      | 1.25     | 6.4   |
| Qwen2.5-0.5B     | Q8    | 0.9      | 0.61     | 13.1  |
| Qwen2.5-1.5B     | F32   | 5.8      | 3.21     | 2.5   |
| Qwen2.5-1.5B     | Q8    | 2.2      | 1.70     | 4.7   |
| Qwen2.5-3B       | F32   | 12.1     | 12.79    | 0.63  |
| Qwen2.5-3B       | Q8    | 4.0      | 2.72     | 2.9   |
| Qwen2.5-7B       | Q8    | 7.4      | 12.62    | 0.63  |

### Observations

- **RSS = GGUF file size**, as the Phase 2 mmap design promises. The
  7B-Q8 model running at 7.4 GB RSS confirms the
  [Phase 2 memory note](../...) (was 19 GB peak pre-Phase-2).
- **Q8 is ~2× faster than F32 at every size.** Memory-bandwidth-bound
  inference; less data per step → faster.
- **3B-F32 and 7B-Q8 land at 0.63 tok/s.** Both move ~10-12 GB of
  weights per token; the gx10's DDR bandwidth (~7-8 GB/s for memcpy
  on aarch64) bottlenecks both. The matmul math is incidental.
- **tok/s × params ≈ ~10 GB/s** across all sizes — a clean
  memory-bandwidth signature. (1.5B-F32: 2.5 × 6 = 15; 1.5B-Q8: 4.7
  × 2.2 = 10.3; 3B-Q8: 2.9 × 4 = 11.6.)

### Caveats for re-running on a clean machine

- Background `pt_data_worker` was at 95% GPU but mostly idle on CPU
  cores. The CPU numbers should be close to clean-machine numbers,
  modulo cache-eviction noise from another tenant's workload.
- A clean run should also measure first-token latency separately
  (we lumped it into the 8-token wall).
- Should sweep N_NEW=64 or 128 to dilute the prefill cost.

## Training (CPU, from-scratch toy)

`demos/train` on the TinyStories toy: vocab=627, d_model=32,
d_ff=64, n_heads=4, n_layers=2, ctx=64, 87 sequences, 1 epoch.

| Metric | Value |
| --- | --- |
| Training wall (1 epoch) | 0.65 s |
| Per-sequence | ~7.5 ms |
| Peak RSS | 39 MB |

This is the **only working training baseline today**. It uses pure
Ruby Mat math (no FFI). Useful as a "training compiles and runs"
proof; not useful for fine-tuning at scale.

## "Baseline for fine-tuning"

The honest answer: **there is no fine-tuning baseline yet**. Real
fine-tuning needs the F0-F4 work in `docs/design/finetuning.md`:

- F0: bind ggml's backward ops through the FFI shim (3-5 days)
- F1: LoRA on CPU on a real model (1-2 weeks)
- F2: LoRA on CUDA (3-5 days after F1)
- ...

When F1 lands, the comparable baseline will be: "Qwen2.5-0.5B
LoRA fine-tune, 1 epoch over N=1000 SFT examples, time + RSS".
Until then, nothing comparable exists.

The numbers above stand in as **inference performance** that any
fine-tuning system will need to beat (forward pass is half the
work).
